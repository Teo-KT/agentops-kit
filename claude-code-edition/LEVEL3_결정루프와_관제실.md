# 레벨 3 — 결정 루프와 관제실

루틴이 열 개를 넘어가면 시스템의 병목이 바뀐다. 처음엔 "AI가 일을 잘 하나"가 문제였는데, 이제는 **"사람의 결정이 시스템에 언제 들어가나"**가 문제가 된다.

이 문서는 그 병목을 다루는 방법이다. 코드보다 **운영 규칙**이 본체이므로, 웹 서버를 안 쓰더라도 읽을 값이 있다.

---

## 1. 유령 대기 — 처음 만나는 벽

각 루틴은 사람의 판단이 필요할 때 보고서에 `needs_user` 한 줄을 남긴다. 브리핑은 그걸 모아 맨 위에 올린다. 여기까지는 잘 된다.

문제는 **결정한 다음**이다. 핸드오프는 고칠 수 없는 기록(append-only)이므로, 어제 결정한 안건도 그 기록 안에 그대로 남아 있고, 오늘 아침 브리핑이 그걸 또 수집한다. 원 시스템에서는 같은 안건에 **사흘 연속 답장하는 사고**가 났다.

**해법: 억제 목록.**

```
dashboard/decided_needs.json   ← 처리된 안건의 키(항목 앞 60자) 목록
```

결정을 처리한 세션은 **반드시** 여기에 키를 추가한다. 브리핑과 화면은 이 목록에 있는 항목을 건너뛴다. 원장은 그대로 두고 뷰에서만 감춘다.

> 규칙 한 줄로 요약하면: **결정을 처리했으면 억제 키를 남긴다.** 이걸 빼먹으면 시스템이 같은 질문을 반복하고, 사람은 곧 브리핑을 안 읽게 된다.

## 2. 중복 상신 — 두 번째 벽

루틴 여럿이 같은 사실을 보면 **같은 안건을 각자 올린다.** 마감 하나를 일정 담당과 관리 담당이 따로 올리는 식이다. 사람 입장에서는 같은 질문이 세 개로 보인다.

**해법: 결정 데스크.**

브리핑 루틴이 게시 직전에 전 루틴의 `needs_user`를 한 번 훑어 ① 중복 통합 ② 품질 4검을 거친 뒤 하나의 목록으로 게시한다.

| 품질 검사 | 내용 |
|---|---|
| 자기완결 | 그 항목만 읽고 판단할 수 있는가 (배경 1문장 + 요청 1문장 + 권고안) |
| 1항목 1결정 | 한 항목에 결정 두 개가 섞여 있지 않은가 |
| 재탕 금지 | 다른 루틴이 이미 올린 안건이 아닌가 |
| 완결 존댓말 | "승인 여부"가 아니라 "승인해 주세요"로 끝나는가 |

마지막 항목이 사소해 보이지만 실제 효과가 크다. **개조식 명사형("확인 필요")은 읽는 사람에게 결정을 요구하지 않는다.** 완결된 요청문이어야 답이 나온다.

## 3. 하루 지연 — 세 번째 벽

브리핑을 보고 "그렇게 해"라고 답해도, 그 답을 실제로 처리하는 건 다음 사이클(원 시스템은 다음 날 새벽)이다. 결정 하나마다 하루가 붙는다.

**해법: 즉시 처리 경로.** 결정 버튼을 누르면 그 자리에서 헤드리스 세션 하나를 띄워 처리한다. 처리 주체가 여럿(정기 당직 · 아침 브리핑 · 즉시 처리)이 되므로, **1번의 억제 키 규칙이 여기서 더 중요해진다.** 누가 처리했든 억제 키는 반드시 남는다.

## 4. 되먹임 — 네 번째 벽

"오늘 우선순위"를 매일 계산해 보여 주면, 곧 이런 상황이 생긴다. 이미 끝낸 일이 계속 위에 떠 있고, 문구가 틀렸는데 고칠 방법이 없다.

**해법: 항목별 피드백.** 우선순위 항목과 루틴 카드 각각에 짧은 피드백 입력을 붙인다.

- 항목: `완료` · `이미 끝냄` · `오늘 안 함` · `내용 수정`
- 루틴: `이렇게 바꿔 주세요` · `오늘은 건너뛰세요` · `지금 다시 실행` · `보고가 부정확합니다`

피드백은 세 곳으로 흐른다. ① 감사 로그 ② 화면 즉시 반영용 겹장부 ③ **담당 루틴 앞으로 쓰는 핸드오프**. 세 번째가 핵심이다. 피드백이 다음 실행의 입력이 되어야 시스템이 실제로 학습한다.

브리핑 루틴에는 "어제 피드백 흡수" 단계를 넣는다. 완료 표시된 항목은 오늘 우선순위에서 빼고, 수정 요청은 문구에 반영한다.

---

## 5. 관제실 화면이 실제로 보여 주는 것

| 탭 | 답하는 질문 |
|---|---|
| 오늘 | 오늘 뭐부터 하나 (사전 계산된 우선순위 + 피드백 입력) |
| 결정 | 내 답을 기다리는 게 뭔가 (정제된 목록 + 결정 이력) |
| 직원 | 각 루틴이 오늘 뭘 했나, 뭐가 빠졌나 |
| 실행 | 지금 도는 작업, 최근 로그 |
| 일정 | 마감·할 일 |
| 질의 | 원장에 대고 자연어로 묻기 |

**결정 이력 탭**에는 상태를 3단으로 표시한다. `처리 완료` / `처리 기록 있음` / `처리 확인 안 됨`. 세 번째가 있는 이유는, **결정만 하고 처리가 안 걸린 건**이 실제로 생기기 때문이다. 그게 눈에 띄지 않으면 조용히 묻힌다.

## 6. 외부 접속

집 밖에서 관제실을 보고 싶다면 **포트를 열지 말고 VPN으로 붙는다**(Tailscale 등). 서버 바인딩은 `127.0.0.1`로 고정한 채, VPN 쪽에서 프록시한다.

두 번째 방법은 **매일 아침 정적 스냅샷을 비공개 웹페이지로 재발행**하는 것이다. 실시간은 아니지만 폰에서 보기 편하고, 서버가 꺼져 있어도 보인다. 이때 **URL은 매번 새로 만들지 말고 같은 주소로 덮어쓴다.** 안 그러면 어제 링크가 죽는다.

## 7. 언제 여기까지 오면 되나

| 신호 | 그럼 |
|---|---|
| 브리핑을 읽고 답장을 안 하게 됐다 | 억제 목록부터 (1번) |
| 같은 질문이 여러 개로 보인다 | 결정 데스크 (2번) |
| 답한 게 다음 날에야 반영된다 | 즉시 처리 (3번) |
| 우선순위가 현실과 어긋난다 | 피드백 (4번) |
| 위 어느 것도 아니다 | **아직 필요 없다** |

순서대로 필요해질 때 하나씩 붙이면 된다. 1번(억제 목록)은 루틴 다섯 개만 넘어가도 곧 필요해지고, 코드 없이 파일 하나로 되니 먼저 해 두면 좋다.
